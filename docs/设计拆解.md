# 《企业私有知识驱动的软件工程辅助系统》Dify复用设计拆解

版本：V1.0

适用对象：课程项目组（胡俊熙、徐涛涛）

## 一、总体设计思路

建议路线：Dify 负责“知识库 + 检索 + 工作流底座”，你们自己负责“软件工程场景业务层 + 前端层”。

核心原则：

1. 不重写 Dify 的底层 RAG 能力。
2. 不直接把 Dify 默认页面作为最终成品。
3. 在 Dify 之上实现培训、交接、设计准备三个场景的业务闭环。

系统分层建议如下：

1. Dify 能力层：知识库、文档切分、向量化、召回、Workflow、LLM 调用、引用返回。
2. 业务层：建议自建一个轻量后端/BFF，根据培训/交接/设计准备模式调用不同 workflow，对 Dify 返回结果做结构化加工。
3. 前端层：使用你们自己的页面承载最终业务交互，不直接让老师看到 Dify 通用控制台。

主线闭环：文档上传入库 -> 检索问答 -> 结构化设计输出 -> 引用与证据追溯。

## 二、哪些部分继续复用 Dify

推荐直接复用：

1. 数据集/知识库管理（datasets）
2. RAG 检索与知识召回能力（rag pipeline / knowledge retrieval node）
3. Workflow 编排能力
4. 模型接入与应用服务 API
5. 基础日志与运行观测能力

不建议当前阶段重写：向量库、索引构建、Embedding 流程、底层模型编排。

## 四、Workflow 清单

| Workflow 名称 | 输入 | 内部能力 | 输出结构 | 说明 |
| --- | --- | --- | --- | --- |
| 通用检索问答 Workflow | 用户问题 + 选定知识库 | 知识检索、Prompt 组织、LLM 生成、引用返回 | 结论 + 依据 + 引用片段 | 作为所有场景的底层通用能力 |
| 培训模式 Workflow | 培训问题 + 场景模式 | 知识检索、术语解释模板、学习路径模板 | 结论 + 背景说明 + 学习建议 + 引用 | 突出“新人理解成本降低” |
| 交接模式 Workflow | 交接问题 + 场景模式 | 知识检索、交接模板、风险模板 | 背景 + 当前进度 + 风险 + 待办 + 引用 | 突出“交接闭环” |
| 设计辅助 Workflow | 设计目标/问题 + 相关知识 | 知识检索、设计模板、结构化生成 | 功能清单 + 详细文本用例 + 模块建议 + 风险 | 这是你们项目的差异化重点 |
| 文档解析摘要 Workflow | 文档内容/文档片段 | 关键信息抽取、摘要、标签生成 | 文档摘要 + 分类建议 + 关键词 | 可用于文档入库后的预处理 |
| 证据不足提示 Workflow | 问题 + 召回结果不足 | 低召回判断、拒答模板 | 证据不足说明 + 建议补充资料 | 体现“不是普通聊天机器人” |

## 六、推荐的实现顺序

1. 第一阶段：只用 Dify 跑通知识库上传、问答、引用展示。
2. 第二阶段：在 Dify 中配置培训模式、交接模式、设计辅助三个 workflow。
3. 第三阶段：开发你们自己的前端页面，对接 Dify API。
4. 第四阶段：增加自己的业务后端，用于统一模式路由、返回结构化数据、记录日志。
5. 第五阶段：补充文档分类、权限、设计输出持久化等能力。

## 七、MVP 范围建议

MVP 必做：

1. 文档上传入库
2. 通用检索问答
3. 引用展示
4. 培训模式
5. 交接模式
6. 一个设计辅助页面

MVP 可暂缓：复杂权限体系、多租户、计费、复杂后台配置、监控大盘。

## 八、最终结论

课程项目阶段建议采用“Dify 做能力底座，你们做业务系统”的路线。

也就是：知识库和检索继续复用 Dify，设计输出、场景模式、页面交互、结构化结果展示由你们自己实现。
